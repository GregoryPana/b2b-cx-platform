# Academic Presentation Content Guidelines

## 1. Argument Structure

### Lead with the research question or platform purpose
State the central question, claim, or purpose explicitly by slide 2 or 3 at the latest. The audience needs it to evaluate everything that follows.

### Use a proven narrative spine

**Option A - Situation / Complication / Resolution (SCR)**
- Situation: what exists today
- Complication: what is missing, broken, risky, or inefficient
- Resolution: what your work or platform changes

**Option B - Funnel + Answer**
- Broad context -> specific gap -> your approach -> key findings -> implications

**Option C - Answer First**
- Lead with the conclusion, then support it
- Useful for boards, governance, and technical leadership audiences

### One argument per presentation
Do not try to present the whole project history. Choose the claim that can be made convincingly in the available time.

### Each slide has one job
Every slide should have a single, clearly defined role in the argument.

### Use the slide area deliberately
Avoid layouts that leave large unused areas on the right or bottom unless whitespace is doing real communication work.
For analytical and platform decks, aim for balanced density:
- enough whitespace to stay readable
- enough content spread to avoid the slide feeling unfinished
- use wider tables, larger diagrams, or better-distributed content blocks instead of letting one half of the slide sit empty

### Flow test
Read slide titles in order. Each should make the next one feel natural.

## 2. Action Titles

Every content slide title should be a complete sentence stating the takeaway.

| Instead of | Use |
|---|---|
| Deployment | Separate DMZ deployment isolates public Mystery Shopper access |
| Authentication | Invitation plus OTP gives stronger verification without external accounts |
| Architecture | The public survey VM reaches only the internal API and database paths it needs |

**Ghost deck test:** read the action titles in sequence. They should tell the full story.

## 3. Exhibit Discipline

### One exhibit per slide
Use one chart, one diagram, one table, or one architecture picture per slide unless a direct side-by-side comparison is necessary.

### Annotate the key finding
Do not make the audience search for the insight. Label it directly.

### Self-sufficient slide test
The slide should still communicate its key point when read later as a PDF.

## 4. Text Discipline

- maximum about 40 words of body text per slide
- bullets are orientation cues, not script replacement
- minimum 20 pt body font
- use bold sparingly for the key point
- use consistent spacing between title, content blocks, and footer so the page feels intentional rather than sparse

## 5. Citations and Attribution

- cite borrowed figures and external data on the slide
- include a references slide at the end
- be consistent in style

## 6. Deck Architecture

Recommended order:

1. Title
2. Why this matters
3. Problem / gap
4. Proposed solution
5. Architecture / flow
6. Deployment / operating model
7. Security / access model
8. Decision options
9. Recommendation
10. Next steps
11. References
12. Appendix

## 7. Timing

- one slide per minute maximum
- rehearse under time
- know which slides can be skipped

## 8. Common Mistakes

- topic labels instead of action titles
- too many ideas on one slide
- unreadable text
- missing recommendation
- ending on “Thank You” instead of conclusions
