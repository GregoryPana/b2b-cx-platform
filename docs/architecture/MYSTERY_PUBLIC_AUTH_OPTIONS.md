# Public Mystery Shopper Authentication — Chosen Solution (Password + TOTP)

This document defines the **single, definitive authentication design** for the
public-facing Mystery Shopper survey deployed on the DMZ VM.

Status: **DECIDED — Option A (Password + TOTP authenticator app).**
Earlier drafts compared signed links, OTP, and link+OTP. That comparison is
closed. The platform will implement Password + TOTP only. Signed links and
email/SMS OTP are explicitly **not** used as the primary mechanism.

Audience:

- Platform Dev (Gregory)
- IT security (Travis)
- Product owners (Maria + Dan)
- Any LLM/engineer implementing the feature (see the companion build guide:
  `docs/architecture/MYSTERY_PUBLIC_2FA_IMPLEMENTATION.md`)

## 1) Background and constraints

The public Mystery Shopper survey is used by external users who:

- are **not** on the internal network in the normal sense,
- are **not** organisational staff,
- do **not** have Microsoft Entra ID accounts.

Additional facts that drive the design:

- The full set of users is **known in advance** (CWS holds their email list).
  There is **no open self-registration**.
- Each user signs an **NDA + waiver** and CWS **installs and configures a VPN**
  on their device. Reaching the DMZ survey frontend at all requires that VPN.
- IT security requires **two-factor authentication** at the application.

Because the user set is known and devices are provisioned in a supervised
onboarding session, the hardest part of any MFA system — securely handing over
the initial second-factor secret — is solved in person and is not exposed to
the open internet.

---

## 2) The chosen model: layered defence

```
Layer 0 (network)  VPN + per-device profile   -> "have"  (keeps all outsiders out)
Layer 1 (app)      Password                    -> "know"
Layer 2 (app)      TOTP authenticator code     -> "have"  (offline, independent channel)
```

The VPN is a network gate, not the application 2FA. The application still
enforces genuine two-factor auth on its own:

- **Factor 1 (something you know):** a per-user password.
- **Factor 2 (something you have):** a time-based one-time password (TOTP)
  generated by an authenticator app (Google Authenticator, Microsoft
  Authenticator, Authy).

Why TOTP rather than email/SMS OTP or magic links:

- TOTP is **offline** — no email/SMS delivery dependency from a locked-down DMZ
  box, no SMS cost, no SIM-swap risk.
- Two secrets delivered to the same email inbox (link + email OTP) collapse to a
  single factor ("whoever controls that inbox"). TOTP is a genuinely
  independent second factor.
- Mystery-shopper results can feed staff performance reviews, so we need strong
  confidence that **the assigned shopper** completed the survey
  (non-repudiation). Per-user accounts with TOTP bind identity far better than
  forwardable per-survey links.

---

## 3) Environment gating — the test VM must NOT use this auth

This is a hard requirement.

- The **test/staging VM** runs the Mystery Shopper frontend **alongside** the
  dashboard and other internal frontends, and is exercised by **internal users
  with Entra logins**. It must keep using **Entra** exactly as today.
- The **DMZ public VM** is the **only** place Password + TOTP is active.

This is controlled by a single switch on each side, defaulting to the existing
Entra behaviour:

- Backend: `AUTH_MODE` env var. `entra` (default) | `mystery_public`.
- Frontend: `VITE_AUTH_MODE` build var. `entra` (default) | `mystery_public`.

Only the DMZ `.env` and the DMZ frontend build set the `mystery_public` value.
Everything else (test VM, internal production) leaves them unset/`entra` and is
**completely unaffected** by this feature.

See the build guide for exactly how the switch is wired.

## 4) User flow

### 4.1 Enrolment (one-time, supervised during NDA + VPN setup)

1. An internal Mystery admin pre-creates the user record from the known email
   list. Status: `invited`.
2. During the onboarding session the user opens the enrolment screen via a
   **single-use enrolment link** (valid ~30 minutes).
3. User sets a password that meets policy.
4. The system generates a TOTP secret and shows a **QR code** plus a manual key.
5. User scans it with their authenticator app.
6. User enters the first 6-digit code to prove the secret enrolled correctly.
   Status becomes `active`.
7. The system shows **8–10 one-time recovery codes**. The user stores them
   safely. These are the self-service escape hatch if the phone is lost.

### 4.2 Login (every session)

1. User connects the CWS VPN.
2. Opens the public Mystery URL; nginx serves the frontend.
3. Enters **email + password**.
4. Backend confirms the email is allow-listed and active, verifies the password
   hash, and returns a **short-lived MFA challenge token** (~5 min, single use).
   No session is issued yet.
5. Frontend prompts for the **6-digit TOTP code**.
6. Backend verifies the code (±1 time-step tolerance, replay-protected) and
   issues the session cookie.
7. User is taken into the survey.

### 4.3 Session lifecycle

- HttpOnly, Secure, SameSite=Strict session cookie (frontend and backend are
  same-origin on the DMZ box, so no cross-site cookie issues).
- **Idle timeout** ~30–60 min plus an **absolute cap** ~8–12 h.
- Surveys can run long, so the idle timeout is **sliding** and survey responses
  **autosave** server-side. A timeout never loses work: the user
  re-authenticates and resumes.

---

## 5) Onboarding & initiation

Fold enrolment into the existing NDA + VPN ceremony:

1. Admin pre-creates the account from the known email list (internal tooling).
2. In the supervised session the user sets their password, scans the
   authenticator QR, enters the confirming code, and records their recovery
   codes.
3. This supervised bootstrap removes the weakest moment of any MFA system — the
   initial secret hand-off — from the open internet.

Provisioning/admin actions (create user, reset, suspend, re-issue enrolment)
run on the **internal** side only. The DMZ box never exposes them.

## 6) Risks and mitigations

| Risk | Mitigation |
| --- | --- |
| **Forgotten password** | Admin-assisted reset (verify identity out-of-band, issue single-use reset link). Self-service email reset is avoided because it would require opening an SMTP relay out of the DMZ. |
| **Lost / replaced phone (TOTP gone)** | User self-recovers with the recovery codes saved at enrolment. If those are also lost, an admin re-issues enrolment after out-of-band identity verification. |
| **Authentication / session expiry mid-survey** | Sliding idle timeout + server-side autosave so no work is lost; user re-authenticates and resumes. Absolute cap bounds risk on a stolen device. |
| **Brute force on password or TOTP** | Per-IP rate limiting on `/api/auth/*` plus per-account soft lockout with exponential backoff and **auto-unlock** (never a permanent lock — that would let an attacker lock out a known email). Password and TOTP failures counted separately. |
| **TOTP replay** | Record the last-used TOTP time-step per user; reject reuse within the window. |
| **Authenticator clock drift** | Accept ±1 time-step; optionally track drift. |
| **Credential sharing** (shopper hands creds to a friend) | TOTP raises the bar; full audit log + VPN device tie deter it. (Hard device-binding is a deliberate non-goal of Option A; if ever required it is a separate future change.) |
| **TOTP secret / password hash at rest** | Password hashes use Argon2id. TOTP secrets are encrypted at rest with an app key held in the DMZ secrets store, never in the DB in plaintext. |
| **Enrolment link interception** | Short expiry, single use, used within the supervised onboarding session. |
| **Account-lockout denial of service** | Soft lockout with auto-unlock timer + IP rate limiting, not permanent locks. |
| **Revocation** | Account status flag (`suspended`) takes effect immediately on next request; active sessions can be revoked server-side (server-side session store). |

## 7) Shared deployment requirements (unchanged from the DMZ guide)

Regardless of auth, the public Mystery deployment still needs:

- a separate public VM in the DMZ,
- HTTPS only,
- a dedicated deploy workflow and runner,
- restricted backend route exposure (only the public auth + survey routes),
- logging and audit trail,
- rate limiting and anti-abuse controls,
- a documented incident-response path.
